Sketchizi Workbench 0.45 — SQL-only fixture execution guard

Current priority: keep the release gate open until a real clean install, production build, external artifact validation, PostgreSQL 17 execution, and rendered-browser run pass.

This milestone hardens the PostgreSQL integration stage further. It accepts only SQL whose bytes exactly match the current known fixture generated through the Workbench SQL artifact generator. This stage is a release-fixture validator, not a generic SQL runner. Modified SQL is rejected before psql runs; files containing psql client meta-commands such as \connect or \! are refused because those commands could change the connection or run shell commands after connection target validation.

The prior database-target safeguards remain active:
- WORKBENCH_POSTGRES_ALLOW_SCHEMA_MUTATION=true is required.
- WORKBENCH_POSTGRES_ALLOW_REMOTE=true is additionally required for non-loopback targets.
- Protected database names such as prod, production, live, and common customer-data variants are refused.

Command on a machine with npm registry access:
  npm run verify:workbench-release

For the PostgreSQL stage, ensure psql is installed and a disposable database is reachable at WORKBENCH_POSTGRES_URL. The default is:
  postgresql://workbench:workbench@127.0.0.1:5432/workbench

Before the local run, explicitly opt in to schema mutation only for the disposable test database:
  $env:WORKBENCH_POSTGRES_ALLOW_SCHEMA_MUTATION = "true"
For a non-loopback test host only, also set:
  $env:WORKBENCH_POSTGRES_ALLOW_REMOTE = "true"
Do not set these for production. The checks are guardrails, not proof that a database is disposable.
